\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
POTLI is a proposed web application for short-term luggage storage at local shops, hotels, and other businesses. It is intended for travelers who need to leave their bags between transport connections, accommodation check-in times, or other activities. The proposed workflow covers finding storage, reserving a time slot, and verifying drop-off and pickup through a QR code or one-time password (OTP). Storage partners would manage capacity and receive payment for completed bookings, while administrators would review partner applications and service records.

This report presents the requirements, system design, prototype implementation, and proposed evaluation. The prototype uses TypeScript and Vite for the frontend, Express for the API, Appwrite for authentication, and PostgreSQL with Drizzle ORM for application profiles. Account access and profile persistence are implemented; listing search, reservations, luggage handoffs, payments, ratings, and administrative operations remain to be developed. The proposed primary evaluation metric is Booking Fulfillment Time (BFT), with a pilot target of a median time no greater than three minutes.

\chapter{Introduction}

\section{Background and Context}
Travelers may need temporary luggage storage before hotel check-in, after check-out, or while waiting for a transport connection. Carrying bags during these intervals limits movement and access to other activities. Storage facilities at stations and airports may not be near the traveler's destination, and availability may be difficult to establish in advance. Local businesses offer a possible alternative where suitable storage space is available.

POTLI is designed to connect travelers with participating businesses and maintain a record of each storage booking. Partners would publish their capacity, opening hours, and prices. The system would record both luggage handoffs, and administrators would review partner details and disputed bookings. Finding a location is therefore only one part of the proposed service; reservation and handoff records are also required.

\section{Problem Statement}
The project addresses the difficulty of finding suitable short-duration luggage storage near a traveler's destination. An informal arrangement may not provide a booking receipt, an availability check, or a consistent record of custody. The proposed system must make these records available without imposing a lengthy procedure on either the traveler or the storage partner.

The interface must be usable on ordinary smartphones and understandable to business owners without technical training. Intermittent connectivity is a further design consideration, particularly during physical handoffs. The project uses standard web technologies and does not require dedicated storage hardware.

\section{Stakeholders}
\begin{itemize}[leftmargin=*]
  \item \textbf{Traveler:} searches, compares locations, books a slot, presents handoff credentials, tracks status, and rates the experience.
  \item \textbf{Storage partner:} registers a business, publishes capacity and hours, confirms drop-off and pickup, and views earnings.
  \item \textbf{Administrator:} verifies partners, audits bookings and fees, reviews reports, and resolves flagged cases.
  \item \textbf{Payment gateway:} processes collections, refunds, payouts, and transaction status in the planned system.
\end{itemize}

\section{Project Objectives}
\begin{enumerate}[leftmargin=*]
  \item Deliver a responsive web interface for traveler discovery, account access, partner onboarding, and role-specific operations.
  \item Implement secure role-based authentication and a persistent data model for travelers, storage partners, and administrators.
  \item Build a booking lifecycle with availability validation, QR/OTP-based drop-off and pickup, timestamps, and photographic handoff evidence.
  \item Instrument the workflow so that median BFT and handoff success can be measured objectively.
  \item Prepare the system for payment settlement, administrative oversight, repeatable deployment, and later geographic scaling.
\end{enumerate}

\chapter{Requirements and System Analysis}

\section{Functional Requirements}
\subsection{Traveler Requirements}
A traveler should be able to search by city, landmark, or proximity; compare price, opening hours, and availability; reserve a time window; receive a booking identifier and QR/OTP; verify both physical handoffs; review current and prior bookings; and submit a post-pickup rating.

\subsection{Partner Requirements}
A partner should be able to create a business profile, submit details for verification, define capacity and operating hours, receive reservations, validate handoff credentials, attach a drop-off photograph, restore capacity after pickup, and review earnings.

\subsection{Administrator Requirements}
An administrator should be able to approve or reject partner applications, inspect users and listings, monitor booking states, audit payment and platform-fee records, review performance summaries, and investigate disputes or suspicious listings.

\section{Non-Functional Requirements}
\begin{itemize}[leftmargin=*]
  \item \textbf{Usability:} short forms, clear role-specific screens, and a mobile-responsive interface.
  \item \textbf{Security:} salted password hashes, signed expiring tokens, authorization checks, server-side validation, secret management, and protected handoff evidence. Authentication controls should follow established web guidance~\cite{owasp-auth}.
  \item \textbf{Reliability:} explicit booking states and idempotent state transitions to avoid duplicate confirmations.
  \item \textbf{Performance:} indexed database queries, pagination, compressed assets, and a median BFT target of at most three minutes.
  \item \textbf{Scalability:} stateless API instances and a database structure that can later support indexed location queries.
  \item \textbf{Maintainability:} versioned endpoints, migration scripts, source-controlled diagram definitions, and clear separation of frontend, API, and data layers.
\end{itemize}

\section{High-Level Architecture}
POTLI uses a three-tier web architecture:
\begin{enumerate}[leftmargin=*]
  \item \textbf{Presentation layer:} a TypeScript application bundled with Vite~\cite{vite}. It renders the public and account pages and uses Appwrite's Web SDK for authentication.
  \item \textbf{Application layer:} an Express~\cite{express} API running on Node.js. The current endpoints are grouped under \path{/api/v1} and provide health checks, login, and authenticated profile access.
  \item \textbf{Data layer:} PostgreSQL~\cite{postgresql}, accessed through a shared Drizzle ORM~\cite{drizzle} workspace and the \texttt{pg} driver. Application roles and partner details are stored here. Appwrite~\cite{appwrite} manages identity and credentials separately.
\end{enumerate}

The browser signs in to Appwrite and requests a JSON Web Token (JWT)~\cite{jwt} for the current session. It sends this token to the backend using the Bearer scheme. The backend asks Appwrite to identify the account and retrieves the corresponding application profile from PostgreSQL. An account without a profile receives a default traveler profile on its first authenticated profile request. Non-browser clients can use the backend login endpoint. Search, booking, photo storage, and payment services have not yet been added.

\chapter{Implementation Details}

\section{Frontend Prototype}
The frontend is written in TypeScript, bundled with Vite, and styled with a responsive stylesheet. A single rendering entry point selects the page from the URL hash. The available pages cover the landing page, traveler and administrator login, partner account access, password recovery, and account summaries. Shared SVG icons and consistent form labels are used across these pages.

Login forms use Appwrite's Web SDK to establish a session. The frontend then requests a JWT and calls \path{/api/v1/auth/me} to obtain the user's profile and role. Each login page checks that the returned role matches the selected account type. This controls page navigation; it does not replace server-side authorization for future booking or administrative operations. Search submission and partner registration are not yet connected to persistent records.

Password-recovery and reset forms call Appwrite's recovery endpoints. The reset page reads the account identifier and recovery secret from the emailed link and removes them from the URL after a successful reset. Email delivery requires the Appwrite mail service to be configured.

\section{Backend Authentication API}
The backend uses TypeScript on Node.js and Express with CORS and JSON middleware. Its main implemented responsibilities are:
\begin{itemize}[leftmargin=*]
  \item checking PostgreSQL connectivity and Appwrite availability through \path{GET /api/v1/health};
  \item submitting email/password credentials to Appwrite and returning a JWT through \path{POST /api/v1/auth/login}; and
  \item identifying the caller through Appwrite, loading or creating the application profile, and returning it through \path{GET /api/v1/auth/me}.
\end{itemize}

The backend identity adapter calls Appwrite's Account API. For server-side login, it carries the session cookie returned by Appwrite to the JWT endpoint. For authenticated requests, it sends the caller's JWT to Appwrite to obtain the account identity. It does not store passwords or implement token signing locally.

The backend database module provides access to the shared Drizzle workspace. A central error handler receives failures from asynchronous routes. All current API routes are versioned.

\section{Database Schema}
The Drizzle schema defines two application tables. The \texttt{profiles} table has a generated UUID primary key, a unique \texttt{appwrite\_user\_id}, email, full name, role, and creation and update timestamps. The role is restricted to \texttt{traveler}, \texttt{storage\_partner}, or \texttt{admin}. The \texttt{partner\_profiles} table stores business name and phone number and references the local profile UUID through a cascading foreign key.

Appwrite accounts are linked by their string identifiers, not by a foreign key to an authentication table. A profile is created by the backend when an authenticated account first requests profile access. This path assigns the traveler role; users cannot supply a different role through that endpoint. The current migration does not define signup triggers or row-level security policies.

SQL migrations are applied in filename order, with completed versions recorded in a \texttt{migrations} table. The development seed script creates or updates Appwrite accounts through the Users API and writes their roles and partner details to PostgreSQL. Seeding requires a server-side Appwrite API key as well as database access.

Later migrations will add the D2--D4 stores for listings, capacity, bookings, handoffs, and transactions. Availability checks and reservation writes must be performed transactionally to prevent concurrent bookings from consuming the same capacity.

\section{Security and Privacy Considerations}
Appwrite manages passwords, sessions, and JWT issuance. The backend identifies a caller before returning the caller's application profile, and it assigns a default role when creating that profile. Database credentials and the administrative API key used for seeding must remain server-side.

Further work is required before public deployment. Protected domain endpoints need server-side role checks, request validation, rate limiting, and audit records. CORS settings must be restricted to the deployed frontend, and error responses must avoid exposing internal database details. Session expiry, revocation, and recovery-link handling also require integration tests. Handoff photographs and personal information will need access controls and defined retention periods. These are requirements for subsequent development, not controls established by the present prototype.

\section{Testing Methodology}
The planned verification strategy combines:
\begin{itemize}[leftmargin=*]
  \item \textbf{Unit tests} for validation, status transitions, pricing, token handling, and utility functions;
  \item \textbf{API integration tests} against an isolated PostgreSQL database for login, authorization, booking races, handoff codes, and invalid transitions;
  \item \textbf{Frontend tests} for route rendering, form behavior, error handling, responsive layout, and accessibility;
  \item \textbf{End-to-end tests} for traveler booking through partner pickup and administrator review;
  \item \textbf{Performance tests} for nearby search and concurrent booking creation; and
  \item \textbf{Pilot user testing} with representative travelers and local businesses.
\end{itemize}

\section{Pilot Plan}
A small locality near a railway station or busy market can provide a controlled first deployment. The proposed pilot includes 8--12 partner businesses and 15--20 traveler participants. Before use, partners receive a brief handoff procedure and the team confirms business details. Application timestamps provide quantitative measures, while structured post-use questions capture convenience, trust, and onboarding difficulty. Any safety incident or disputed handoff takes priority over performance measurement.

\chapter{Conclusion}

\section{Summary of Work}
The work completed so far includes requirements analysis, the system architecture, data flow and UML models, a responsive frontend, a versioned authentication API, and an application profile schema. The prototype connects Appwrite account access with PostgreSQL profile persistence.

The prototype does not yet provide a complete luggage-storage service. Listing search, reservations, QR/OTP handoffs, payments, ratings, and administrative operations remain to be implemented and tested.

\section{Key Findings}
\begin{itemize}[leftmargin=*]
  \item A booking record must retain the information needed to verify custody: handoff credentials, timestamps, and photographic evidence.
  \item Availability and booking creation form the central consistency boundary; they must be updated transactionally to prevent overbooking.
  \item Account identity is managed by Appwrite. PostgreSQL stores application roles and business records.
  \item The BFT target is useful only when timestamps and state definitions are implemented before pilot measurement.
\end{itemize}

\section{Future Work and Recommendations}
\begin{enumerate}[leftmargin=*]
  \item Implement listing management and indexed location search.
  \item Add transactional booking creation and dynamic QR/OTP credentials.
  \item Build protected partner handoff screens with secure photo upload.
  \item Introduce role-authorization middleware and comprehensive automated tests.
  \item Integrate a sandbox payment gateway before enabling real collections or payouts.
  \item Build administrator verification, audit, analytics, and dispute tools.
  \item Deploy a staging environment, run the proposed pilot, and replace target values with measured results.
\end{enumerate}

\section{Final Remarks}
The next milestone is a tested workflow from listing search to verified pickup. It must include a reliable capacity check, a persistent booking record, and both handoff confirmations. Completing this workflow will allow the team to measure BFT and evaluate the service with the proposed pilot participants.
